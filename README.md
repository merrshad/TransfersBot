# پل دوطرفه بله ↔ تلگرام

ربات آمادهٔ استقرار برای انتقال دوطرفهٔ متن، عکس، فایل و سایر رسانه‌ها بین
تلگرام و بله است. هر کاربر یک حساب در هر پیام‌رسان دارد و دو کاربر با
دستورهای داخل ربات به هم «جفت» می‌شوند؛ از آن به بعد پیام‌های هر کدام برای
دیگری بازتاب داده می‌شود.

این نسخه شامل قابلیت‌های فازهای قبل است: ثبت‌نام و جفت‌سازی، انتقال متن و
رسانه، صف پایدار `outbox`، تلاش مجدد با backoff، محدودیت نرخ ارسال،
ذخیرهٔ offset، خاموشی تمیز و `/status` عملیاتی. سینک چند جفت‌گروه نیز با
دکمه‌های شیشه‌ای پشتیبانی می‌شود؛ مالک ربات مستقیم وصل می‌کند و ادمین‌های
گروه با تأیید ادمین گروه مقصد. برای استقرار، دو راه دارید: اجرای مستقیم با
Python یا اجرا با Docker Compose.

> **هشدار امنیتی:** توکن ربات مثل رمز عبور است. آن را در گیت، چت، اسکرین‌شات
> یا لاگ قرار ندهید. اگر توکنی جایی منتشر شد، فوراً در BotFather آن را
> revoke و توکن جدید بسازید. فایل `.env` در `.gitignore` است و از context
> ساخت Docker هم حذف می‌شود.

## ۱. پیش‌نیازها

- Python نسخهٔ **3.11 یا 3.12** برای اجرای بدون Docker.
- **Docker Engine 24+** و **Docker Compose v2+** برای اجرای کانتینری.
- یک سرور یا VPS با دسترسی خروجی HTTPS (پورت ۴۴۳). ربات از long polling
  استفاده می‌کند و **به هیچ پورت ورودی نیاز ندارد**.
- دسترسی به API تلگرام (`api.telegram.org`). اگر سرور داخل ایران است،
  تلگرام معمولاً در دسترس نیست؛ بخش
  [استقرار و دسترسی شبکه](#۱۰-استقرار-و-دسترسی-شبکه) را بخوانید.
- دسترسی به API بله (`tapi.bale.ai`).
- دو توکن ربات: یکی از BotFather تلگرام و یکی از BotFather بله.

## ۲. ساخت ربات تلگرام

1. در تلگرام به `@BotFather` پیام بدهید.
2. دستور `/newbot` را بزنید.
3. یک **نام نمایشی** (مثلاً `Bale Telegram Bridge`) و یک **username** که به
   `bot` ختم می‌شود (مثلاً `my_bridge_bot`) انتخاب کنید.
4. BotFather یک توکن به شکل زیر می‌دهد:

   ```text
   123456789:AAExampleTokenDoNotUseThisValue
   ```

   این مقدار را در `.env` و در متغیر `TELEGRAM_BOT_TOKEN` بگذارید.
5. ربات را باز کنید و `/start` بفرستید تا بتواند به شما پیام بدهد.
6. برای دریافت شناسهٔ عددی خودتان، به `@userinfobot` پیام بدهید یا از
   `getUpdates` استفاده کنید (بخش بعد).

> اگر توکن لو رفت، در BotFather دستور `/revoke` را بزنید و توکن جدید را
> جایگزین کنید. توکن قدیمی دیگر کار نمی‌کند.

## ۳. ساخت بازوی بله

بله هم مانند تلگرام یک BotFather دارد. مستندات رسمی:

- <https://docs.bale.ai>
- ساخت بازو: <https://ble.ir/botfather>

مراحل:

1. در اپلیکیشن بله، بازوی `@botfather` را جستجو کنید یا
   <https://ble.ir/botfather> را باز کنید.
2. `/start` و سپس `/newbot` را بفرستید.
3. نام و username بازو را انتخاب کنید.
4. توکنی مشابه نمونهٔ زیر دریافت می‌کنید (این نمونهٔ مستندات است، نه توکن
   واقعی):

   ```text
   123456789:abcdIuZmK5qNEm2A1BhUaAg7MPJv1O9KCcBQB2ro
   ```

5. توکن را در `.env` و در متغیر `BALE_BOT_TOKEN` قرار دهید.
6. بازو را باز کنید و `/start` بفرستید.
7. آدرس پایهٔ API بله `https://tapi.bale.ai` است و در `.env` به صورت
   `BALE_API_BASE_URL=https://tapi.bale.ai` تنظیم می‌شود. اگر از درگاه
   دیگری استفاده می‌کنید، همان را وارد کنید.

مستندات بله تأکید می‌کند که API آن با API تلگرام سازگار است؛ بنابراین همین
پروژه هم از یک لایهٔ adapter برای هر دو استفاده می‌کند. برای دریافت
آپدیت‌ها، `getUpdates` با long polling استفاده می‌شود.

## ۴. شناسه‌های پلتفرمی و شناسهٔ کاربری پل

در `.env` دو شناسهٔ **عددی پلتفرمی** لازم است:

- `TELEGRAM_OWNER_ID`: شناسهٔ عددی شما در تلگرام.
- `BALE_OWNER_ID`: شناسهٔ عددی شما در بله.

این‌ها با «شناسهٔ کاربری پل» که `/whoami` نشان می‌دهد فرق دارند. شناسهٔ پل یک
رشتهٔ کوتاه و تصادفی مثل `A7K9Q2M4` است و برای `/pair`، `/ban` و `/unban`
استفاده می‌شود؛ شناسهٔ عددی پلتفرمی فقط برای تنظیم مالک و ارسال پیام سیستمی
است.

### تلگرام

روش ساده: به `@userinfobot` پیام بدهید؛ عدد `Id` را بردارید.

روش مطمئن‌تر با `getUpdates` (توکن را در shell تاریخچه ذخیره نکنید):

```bash
export TELEGRAM_BOT_TOKEN='توکن-خودتان'
curl -s "https://api.telegram.org/bot${TELEGRAM_BOT_TOKEN}/getUpdates"
```

در خروجی، مقدار `message.from.id` (یا `message.chat.id` در chat خصوصی) همان
شناسهٔ عددی است.

### بله

بعد از اینکه یک بار به بازو پیام دادید، `getUpdates` را صدا بزنید:

```bash
export BALE_BOT_TOKEN='توکن-خودتان'
curl -s "https://tapi.bale.ai/bot${BALE_BOT_TOKEN}/getUpdates"
```

در هر update، مقدار `result[].message.from.id` شناسهٔ عددی کاربر است. اگر
chat خصوصی باشد، `message.chat.id` هم معمولاً همان مقدار است.

> اگر خروجی خالی بود، ابتدا در بله به بازو `/start` بفرستید و دوباره
> `getUpdates` را اجرا کنید. توکن را در فایل‌های عمومی یا اسکرین‌شات قرار
> ندهید.

## ۵. تنظیمات `.env`

```bash
cp .env.example .env
```

سپس `.env` را باز کنید و حداقل این چهار مقدار را پر کنید:

```dotenv
TELEGRAM_BOT_TOKEN=...
BALE_BOT_TOKEN=...
TELEGRAM_OWNER_ID=...
BALE_OWNER_ID=...
```

نمونهٔ حداقلی برای یک استقرار عمومی:

```dotenv
TELEGRAM_BOT_TOKEN=...
BALE_BOT_TOKEN=...
TELEGRAM_OWNER_ID=123456789
BALE_OWNER_ID=123456789

DB_PATH=data/bridge.db
LOG_LEVEL=INFO

MAX_USERS=500
MAX_PAIRS_PER_USER=1

RATE_LIMIT_ENABLED=true
USER_MESSAGES_PER_MINUTE=30
USER_RATE_LIMIT_ACTION=queue

HEALTHCHECK_FILE=data/health
```

متغیرهای مهم:

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | — | الزامی؛ توکن BotFather تلگرام |
| `BALE_BOT_TOKEN` | — | الزامی؛ توکن BotFather بله |
| `TELEGRAM_OWNER_ID` | — | الزامی؛ شناسهٔ عددی مالک در تلگرام |
| `BALE_OWNER_ID` | — | الزامی؛ شناسهٔ عددی مالک در بله |
| `BALE_API_BASE_URL` | `https://tapi.bale.ai` | آدرس API بله |
| `DB_PATH` | `data/bridge.db` | فایل SQLite؛ پوشهٔ والد خودکار ساخته می‌شود |
| `LOG_LEVEL` | `INFO` | `DEBUG`/`INFO`/`WARNING`/`ERROR`/`CRITICAL` |
| `POLL_TIMEOUT_SECONDS` | `25` | زمان long polling |
| `MAX_USERS` | `0` | سقف کل کاربران؛ `0` یعنی نامحدود |
| `MAX_PAIRS_PER_USER` | `1` | حداکثر جفت فعال هر کاربر |
| `PAIR_REQUEST_TTL_HOURS` | `24` | مهلت درخواست جفت‌سازی |
| `TELEGRAM_BOT_USERNAME` | `Tele_to_Bale_RoBot` | نام کاربری ربات تلگرام برای لینک عمیق |
| `BALE_BOT_USERNAME` | `bale2telrobot` | نام کاربری ربات بله برای لینک عمیق |
| `PAIR_INVITE_TTL_MINUTES` | `15` | اعتبار لینک یک‌بارمصرف جفت‌سازی |
| `MEDIA_ENABLED` | `true` | فعال بودن انتقال رسانه |
| `MEDIA_TEMP_DIR` | `data/tmp` | پوشهٔ موقت فایل‌ها |
| `MEDIA_USER_QUOTA_MB` | `200` | سقف فضای موقت هر کاربر |
| `OUTBOX_MAX_ATTEMPTS` | `5` | سقف تلاش ارسال |
| `OUTBOX_RETRY_BASE_SECONDS` | `10` | اولین تأخیر retry |
| `OUTBOX_RETRY_JITTER` | `0.2` | jitter به صورت کسری (±۲۰٪) |
| `OUTBOX_MEDIA_TIMEOUT_TERMINAL` | `true` | تایم‌اوت رسانه به‌جای retry، failed می‌شود تا فایل تکراری ارسال نشود |
| `OUTBOX_SENT_RETENTION_DAYS` | `7` | ردیف‌های `sent` بدون محتوا بعد از این تعداد روز پاک می‌شوند (`0` = غیرفعال) |
| `SHUTDOWN_TIMEOUT_SECONDS` | `30` | مهلت پایان ارسال در جریان |
| `TELEGRAM_CONNECT_TIMEOUT_SECONDS` | `30` | timeout اتصال Telegram |
| `TELEGRAM_READ_TIMEOUT_SECONDS` | `300` | timeout خواندن/دانلود Telegram |
| `TELEGRAM_WRITE_TIMEOUT_SECONDS` | `600` | timeout آپلود Telegram |
| `RATE_LIMIT_ENABLED` | `true` | کلید کلی rate limit |
| `TELEGRAM_GLOBAL_MESSAGES_PER_SECOND` | `25` | سقف سراسری تلگرام |
| `BALE_GLOBAL_MESSAGES_PER_SECOND` | `20` | سقف سراسری بله |
| `TELEGRAM_CHAT_MESSAGES_PER_SECOND` | `1` | سقف هر chat تلگرام |
| `BALE_CHAT_MESSAGES_PER_SECOND` | `1` | سقف هر chat بله |
| `USER_MESSAGES_PER_MINUTE` | `30` | ضد اسپم برای هر فرستنده |
| `USER_RATE_LIMIT_ACTION` | `queue` | `queue` یا `reject` |
| `HEALTHCHECK_FILE` | — | فایل heartbeat برای Docker |
| `HEALTHCHECK_MAX_AGE_SECONDS` | `90` | حداکثر عمر مجاز heartbeat |

فهرست کامل و توضیح هر متغیر در `.env.example` آمده است. `.env` را کامیت
نکنید.

## ۶. اجرای لوکال بدون Docker

### Linux / macOS

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"

cp .env.example .env
# ویرایش .env و پر کردن توکن‌ها و owner idها

python main.py
```

### Windows (PowerShell)

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"

Copy-Item .env.example .env
# ویرایش .env

$env:PYTHONIOENCODING = "utf-8"
.\.venv\Scripts\python.exe main.py
```

نکته‌های اجرا:

- توقف با `Ctrl+C` انجام می‌شود؛ ربات SIGINT را می‌گیرد، polling را متوقف
  می‌کند، ارسال در جریان را تمام می‌کند و اتصال‌ها را می‌بندد.
- دیتابیس و فایل‌های موقت در مسیرهای `DB_PATH` و `MEDIA_TEMP_DIR` ساخته
  می‌شوند. پوشهٔ `data/` باید قابل نوشتن باشد.
- اگر پشت proxy هستید، متغیرهای استاندارد `HTTPS_PROXY`/`HTTP_PROXY` را
  تنظیم کنید. کتابخانهٔ `httpx` و `python-telegram-bot` از آن‌ها استفاده
  می‌کنند.
- برای دیدن لاگ‌ها `LOG_LEVEL=INFO` کافی است. محتوای پیام‌ها در INFO ثبت
  نمی‌شود؛ فقط شناسه‌ها، نوع رویداد و وضعیت.

## ۷. اجرا با Docker Compose

### آماده‌سازی

```bash
cp .env.example .env
# ویرایش .env؛ حتماً توکن‌ها و owner idها را بگذارید
```

`.env` باید وجود داشته باشد، چون `docker-compose.yml` آن را با `env_file`
می‌خواند. این فایل در `.gitignore` و `.dockerignore` است.

### ساخت و اجرا

```bash
docker compose build
docker compose up -d
docker compose ps
```

در خروجی `ps`، ستون `STATUS` باید بعد از حدود ۲۰ تا ۳۰ ثانیه شامل
`healthy` شود. برای دیدن لاگ:

```bash
docker compose logs -f --tail=200
```

توقف و حذف کانتینر (دیتابیس در volume می‌ماند):

```bash
docker compose down
```

حذف کامل داده‌ها (احتیاط؛ دیتابیس و فایل‌های موقت پاک می‌شوند):

```bash
docker compose down -v
```

### volumeها

| volume | مسیر داخل کانتینر | محتوا |
|---|---|---|
| `bridge-db` | `/app/data` | `bridge.db`، `bridge.db-wal`، `bridge.db-shm`، heartbeat |
| `bridge-media` | `/app/media` | فایل‌های موقت بین دانلود و آپلود |

`docker-compose.yml` این مسیرها را با `environment` روی مقادیر داخل volume
تنظیم می‌کند؛ بنابراین مقادیر `DB_PATH` و `MEDIA_TEMP_DIR` در `.env` برای
حالت Compose بازنویسی می‌شوند.

### healthcheck

`Dockerfile` یک `HEALTHCHECK` دارد که هر ۳۰ ثانیه `healthcheck.py` را اجرا
می‌کند. این اسکریپت فایل `HEALTHCHECK_FILE` را می‌خواند و سه چیز را بررسی
می‌کند:

1. فایل وجود دارد؛
2. عمر آن از `HEALTHCHECK_MAX_AGE_SECONDS` کمتر است؛
3. وضعیت نوشته‌شده `ok` است.

اگر worker از کار بیفتد یا آخرین pass خطا بدهد، health قرمز می‌شود. برای
بررسی دستی:

```bash
docker compose exec bridge python healthcheck.py
```

### به‌روزرسانی

```bash
git pull
docker compose up -d --build
docker compose ps
```

### اجرای امن

کانتینر با کاربر غیر root (UID/GID `10001`) اجرا می‌شود، `cap_drop: ALL` و
`no-new-privileges` دارد، پورت ورودی باز نمی‌کند و `restart: unless-stopped`
است. `stop_grace_period` روی ۴۵ ثانیه تنظیم شده تا worker فرصت پایان ارسال
داشته باشد.

## ۸. جفت‌سازی برای کاربران نهایی

هر دو نفر باید یک حساب در پیام‌رسان خودشان داشته باشند. لازم نیست هر دو در
یک پیام‌رسان باشند؛ مثلاً یکی در تلگرام و دیگری در بله.

### گام‌به‌گام (روش خودکار — پیشنهادی)

1. در یکی از پیام‌رسان‌ها ربات را باز کنید و `/start` بفرستید.
2. در پیام خوش‌آمد، دکمهٔ **«🔗 جفت‌سازی»** را بزنید.
3. ربات یک **لینک یک‌بارمصرف** به ربات پیام‌رسان مقابل می‌سازد:
   - از بله → ربات تلگرام باز می‌شود.
   - از تلگرام → ربات بله باز می‌شود.
4. روی دکمهٔ لینک بزنید و در ربات مقابل `/start` را بزنید.
5. جفت‌سازی **به‌صورت خودکار** انجام می‌شود و هر دو طرف پیام تأیید
   می‌گیرند. دیگر لازم نیست شناسهٔ طرف مقابل را بفرستید یا درخواست را
   دستی تأیید کنید.

> لینک جفت‌سازی **یک‌بارمصرف** و به‌طور پیش‌فرض **۱۵ دقیقه** معتبر است
> (`PAIR_INVITE_TTL_MINUTES`). اگر منقضی شد، دوباره دکمهٔ «🔄 لینک جدید»
> را بزنید. این لینک را برای دیگران نفرستید؛ هر کسی که آن را باز کند
> می‌تواند جفت‌سازی را کامل کند.

### روش جایگزین (با شناسه)

اگر لینک را نمی‌خواهید:

1. هر دو کاربر `/start` بزنند.
2. هر کاربر با `/whoami` شناسهٔ کوتاه خود را ببیند (مثلاً `A7K9Q2M4`).
3. یک طرف `/pair <شناسه طرف مقابل>` بفرستد.
4. طرف مقابل با `/pending` درخواست را ببیند و با دکمهٔ «✅ پذیرش» یا
   `/accept <request_id>` بپذیرد.

### بعد از اتصال

از این لحظه هر متن، عکس، ویدیو، فایل، استیکر یا آلبومی که یکی بفرستد
برای دیگری بازتاب داده می‌شود. پاسخ‌ها (reply) هم تا حد امکان به پیام
متناظر در سمت مقابل وصل می‌شوند.

برای دیدن وضعیت: `/status`

برای پایان دادن به جفت: `/unpair` یا اگر چند جفت دارید:
`/unpair <شناسه جفت>`

### دستورهای کاربر

| دستور | کار |
|---|---|
| `/start` | ثبت‌نام و راهنمای شروع |
| `/help` | راهنمای دستورها |
| `/whoami` | نمایش شناسهٔ تصادفی کاربری، پلتفرم، نقش و وضعیت |
| `/status` | وضعیت جفت‌ها و درخواست‌های خودتان |
| `/pair` | ساخت لینک خودکار جفت‌سازی با پلتفرم مقابل |
| `/pair <public_id>` | روش جایگزین: ارسال درخواست به شناسهٔ کاربر |
| `/pending` | نمایش درخواست‌های دریافتی |
| `/accept <request_id>` | پذیرش درخواست |
| `/reject <request_id>` | رد درخواست |
| `/cancel <request_id>` | لغو درخواست ارسالی |
| `/unpair [pair_id]` | پایان دادن به جفت فعال |

نکته‌ها:

- هر کاربر به‌طور پیش‌فرض فقط یک جفت فعال می‌تواند داشته باشد
  (`MAX_PAIRS_PER_USER`).
- درخواست جفت‌سازی تا `PAIR_REQUEST_TTL_HOURS` ساعت معتبر است.
- اگر کاربر مقابل ربات را بلاک کرده باشد، نوتیفیکیشن تحویل نمی‌شود و
  درخواست به‌صورت خودکار لغو می‌شود.
- کاربر مسدود (`banned`) نمی‌تواند جفت جدید بسازد، ولی می‌تواند
  `/status`، `/help`، `/cancel` و `/unpair` را اجرا کند.

### منوهای شیشه‌ای (Inline Keyboard)

بیشتر کارها با دکمه‌های شیشه‌ای زیر پیام انجام می‌شوند:

- `/start` منوی اصلی را با دکمه‌های «📊 وضعیت»، «🔗 جفت‌سازی»،
  «📥 درخواست‌ها»، «👤 پروفایل» و «❓ راهنما» نشان می‌دهد.
- «🔗 جفت‌سازی» یک لینک عمیق به ربات پیام‌رسان مقابل می‌سازد
  (`t.me/...` یا `ble.ir/...`) تا با یک استارت، جفت‌سازی خودکار شود.
- پیام درخواست جفت‌سازی (روش جایگزین) برای طرف مقابل، دکمه‌های
  «✅ پذیرش» و «❌ رد» دارد.
- `/pending` برای هر درخواست، دکمهٔ پذیرش/رد همان درخواست را نشان می‌دهد.
- `/status` برای هر جفت فعال، دکمهٔ «🔓 پایان جفت» دارد.
- مالک در «🛠 مدیریت» به فهرست کاربران و دکمه‌های مسدود/رفع‌مسدودی
  دسترسی دارد.
- دکمه‌هایی که به شناسه نیاز دارند (مثل `/pair` و `/ban`) یک پیام راهنما
  باز می‌کنند و دستور متنی معادل را نشان می‌دهند؛ چون دکمهٔ شیشه‌ای
  نمی‌تواند عدد تایپ کند.
- دکمه‌ها پیام را در همان‌جا ویرایش می‌کنند؛ اگر ویرایش ممکن نباشد
  (پیام قدیمی)، نسخهٔ جدید ارسال می‌شود.
- دکمه‌های قدیمی بعد از تغییر وضعیت ممکن است خطای «دیگر معتبر نیست»
  بدهند؛ از «🏠 منوی اصلی» ادامه دهید.

## ۹. دستورات مالک

مالک با `TELEGRAM_OWNER_ID`/`BALE_OWNER_ID` شناخته می‌شود و باید یک بار
`/start` بفرستد تا در دیتابیس ثبت شود.

| دستور | کار |
|---|---|
| `/status` | آمار کلی: کاربران فعال، جفت‌های فعال، طول صف، خطاهای ۲۴ ساعت، آخرین رله |
| `/users [n]` | فهرست `n` کاربر آخر (پیش‌فرض ۵۰، حداکثر ۵۰) |
| `/ban <user_id>` | مسدود کردن کاربر |
| `/unban <user_id>` | رفع مسدودی |

`/status` مالک شامل این خطوط است:

```text
وضعیت کلی پل:
  کاربران: ...
  کاربران فعال: ...
  جفت‌های فعال: ...
  درخواست‌های در انتظار: ...
  صف ارسال: ...
  خطاهای ۲۴ ساعت گذشته: ...
  آخرین رله: ...
```

`user_id` در `/ban` و `/unban` همان **شناسهٔ کوتاه پل** است که `/whoami`
یا `/users` نشان می‌دهد، نه شناسهٔ عددی تلگرام/بله.

## ۱۰. استقرار و دسترسی شبکه

### تلگرام

API تلگرام (`api.telegram.org`) از داخل ایران معمولاً فیلتر است. چون ربات
باید هم‌زمان به تلگرام و بله وصل باشد، ساده‌ترین راه **استقرار سرور خارج از
ایران** است (VPS در آلمان، فنلاند، هلند و…). چند نکته:

- سرور باید به `api.telegram.org` و `tapi.bale.ai` دسترسی خروجی HTTPS
  داشته باشد.
- فقط پورت ۴۴۳ خروجی لازم است؛ نیازی به باز کردن پورت ورودی نیست.
- اگر سرور داخل ایران است، برای تلگرام به proxy/VPN معتبر نیاز دارید و
  باید `HTTPS_PROXY` را تنظیم کنید. پایداری این روش به کیفیت proxy بستگی
  دارد و برای production توصیه نمی‌شود.
- اگر سرور خارج از ایران است، بله از خارج هم در دسترس است؛ اما latency
  بیشتری دارد. قبل از استقرار تست کنید:

  ```bash
  curl -I https://api.telegram.org
  curl -I https://tapi.bale.ai
  ```

- ساعت سرور را با NTP هم‌زمان کنید؛ timestampها و offsetها به زمان
  وابسته‌اند.

### بله

API بله از داخل ایران در دسترس است و آدرس آن `https://tapi.bale.ai` است.
اگر سرور خارج از ایران است، همان‌جا هم قابل استفاده است. برای جزئیات
مستندات رسمی را ببینید: <https://docs.bale.ai>.

### محدودیت‌های قانونی و عملیاتی

- انتقال پیام بین دو پیام‌رسان را فقط برای کاربرانی فعال کنید که با
  شرایط استفاده و حریم خصوصی شما موافقت کرده‌اند.
- محتوای پیام‌ها در دیتابیس پل ذخیره نمی‌شود؛ فقط متن/کپشن در payload صف
  تا زمان ارسال می‌ماند. با این حال، دیتابیس و volumeها را محافظت و
  backup کنید.
- برای حجم بالا، یک worker و یک دیتابیس کافی است؛ چند نمونهٔ هم‌زمان روی
  یک دیتابیس پشتیبانی نمی‌شود.

## ۱۱. امنیت و محافظت‌ها

### ثبت‌نام باز

به‌طور پیش‌فرض هر کسی که ربات را پیدا کند می‌تواند `/start` بزند و ثبت‌نام
کند. برای استقرار عمومی حتماً:

- `MAX_USERS` را روی یک عدد واقعی بگذارید (مثلاً `500`). مقدار `0` یعنی
  نامحدود و برای production توصیه نمی‌شود.
- `MAX_PAIRS_PER_USER` را روی `1` یا عددی کوچک نگه دارید.
- rate limitها را فعال نگه دارید:
  - `USER_MESSAGES_PER_MINUTE` ضد اسپم است؛
  - `TELEGRAM_CHAT_MESSAGES_PER_SECOND` و
    `BALE_CHAT_MESSAGES_PER_SECOND` از flood روی یک chat جلوگیری می‌کنند؛
  - `*_GLOBAL_MESSAGES_PER_SECOND` سقف سراسری هر پلتفرم است.
- `USER_RATE_LIMIT_ACTION=queue` پیام اضافی را نگه می‌دارد و به کاربر
  راهنما می‌دهد؛ `reject` پیام اضافی را رد می‌کند.
- کاربران مشکوک را با `/ban` مسدود کنید. کاربر مسدود نمی‌تواند جفت جدید
  بسازد یا پیام رله کند.
- **شناسه‌های کاربری تصادفی‌اند، نه رمز.** شناسهٔ ۸ کاراکتری با الفبای
  ۳۲تایی حدود ۴۰ بیت آنتروپی دارد و شمارش سادهٔ `1, 2, 3, …` را غیرعملی
  می‌کند؛ اما هر کسی که شناسه را ببیند می‌تواند درخواست جفت‌سازی بفرستد.
  امنیت واقعی از پذیرش درخواست توسط طرف مقابل، rate limit و ban می‌آید.
  شناسه را مثل یک نام کاربری عمومی بدانید، نه توکن احراز هویت.

### توکن‌ها و لاگ‌ها

- توکن‌ها فقط در `.env` نگه داشته می‌شوند و در `repr` تنظیمات به صورت
  `SecretStr` پوشانده می‌شوند.
- لاگرهای `httpx`، `httpcore` و `telegram` روی `WARNING` قفل شده‌اند و یک
  filter توکن‌ها را از پیام‌ها و tracebackها پاک می‌کند.
- لاگ‌های INFO فقط شناسه، نوع رویداد، وضعیت و زمان‌ها را دارند؛ متن پیام
  یا کپشن در INFO ثبت نمی‌شود.
- اگر توکنی در چت، issue، لاگ یا اسکرین‌شات منتشر شد، آن را revoke کنید.
  صرفاً حذف فایل کافی نیست.

### فایل‌ها و volumeها

- `bridge-db` شامل دیتابیس SQLite و heartbeat است. دسترسی آن را محدود
  کنید.
- `bridge-media` فایل‌های موقت است و پس از ارسال یا شکست نهایی پاک
  می‌شود. `MEDIA_USER_QUOTA_MB` سقف مصرف هر کاربر را کنترل می‌کند.
- از دیتابیس backup دوره‌ای بگیرید. برای SQLite بهتر است backup از
  `bridge.db` همراه با `-wal` و `-shm` یا با `sqlite3 .backup` انجام شود.

## ۱۳. عیب‌یابی

### `docker compose up` بالا نمی‌آید

- مطمئن شوید `.env` وجود دارد: `ls -la .env`.
- خروجی `docker compose config` را ببینید تا خطای env مشخص شود.
- لاگ‌ها: `docker compose logs --tail=100 bridge`.
- اگر خطای `ValidationError` دیدید، یکی از چهار متغیر الزامی خالی است.

### healthcheck قرمز است

```bash
docker compose exec bridge python healthcheck.py
docker compose logs --tail=100 bridge
```

- اگر فایل heartbeat وجود ندارد، worker هنوز شروع نشده یا `/app/data`
  قابل نوشتن نیست.
- اگر فایل کهنه است، worker در یک pass گیر کرده یا process مرده است.
- اگر وضعیت `degraded` است، آخرین pass خطا داده؛ لاگ را ببینید.

### خطای توکن تلگرام

- `InvalidToken`/`Unauthorized`: توکن را از BotFather دوباره بگیرید.
- `Forbidden: bot was blocked by the user`: کاربر ربات را بلاک کرده؛
  پیام به او تحویل نمی‌شود.
- `chat not found`: کاربر هنوز `/start` نزده یا chat id اشتباه است.

### خطای بله

- `403`/`404` یا پیام «کاربر یافت نشد»: کاربر باید ابتدا بازو را استارت
  کند.
- اگر `getUpdates` خالی است، مطمئن شوید هیچ webhook فعالی روی همان بازو
  نیست؛ این پروژه از long polling استفاده می‌کند.
- مستندات: <https://docs.bale.ai>

### `database is locked`

- فقط **یک** نمونه از ربات را روی یک فایل SQLite اجرا کنید.
- اگر دو کانتینر با volume مشترک بالا آورده‌اید، یکی را متوقف کنید.

### پیام‌ها ارسال نمی‌شوند

- `/status` را به‌عنوان مالک بزنید: طول صف، خطاهای ۲۴ ساعت و آخرین رله را
  ببینید.
- اگر `failed` زیاد است، دلیل در `last_error` دیتابیس است.
- rate limit را موقتاً بالا ببرید یا `USER_RATE_LIMIT_ACTION` را بررسی
  کنید.
- health و لاگ worker را ببینید.

### فایل‌های موقت پر شده‌اند

- `MEDIA_USER_QUOTA_MB` را بررسی کنید.
- فایل‌های کهنه بعد از ۲۴ ساعت در startup پاک می‌شوند.
- فضای volume `bridge-media` را ببینید.

### تفاوت شناسه‌ها

- `TELEGRAM_OWNER_ID`/`BALE_OWNER_ID`: شناسهٔ عددی پلتفرم.
- `/whoami`: شناسهٔ کوتاه و تصادفی پل (مثل `A7K9Q2M4`) برای `/pair` و
  `/ban`.
- شناسهٔ پل عمداً از حروف/اعداد بدون `0/O/1/I` ساخته می‌شود تا خواندن و
  تایپ آن راحت باشد. این شناسه یک **شناسه** است، نه رمز؛ دانستن آن به
  تنهایی اجازهٔ جفت‌سازی نمی‌دهد و طرف مقابل باید درخواست را بپذیرد.

## ۱۵. معماری و قابلیت اطمینان

- **شناسهٔ کاربری:** هر کاربر علاوه بر کلید عددی داخلی، یک `public_id`
  تصادفی ۸ کاراکتری دارد (مثل `A7K9Q2M4`) که در `/whoami`، `/pair`،
  `/ban` و `/users` دیده می‌شود. schema v4 این ستون را اضافه و برای
  کاربران قبلی backfill می‌کند. شناسهٔ عددی داخلی برای foreign keyها
  باقی می‌ماند و به کاربر نمایش داده نمی‌شود.
- **صف پایدار:** پیام ابتدا در `messages` و `outbox` (در یک تراکنش) ثبت
  می‌شود. وضعیت‌ها `pending`، `sending`، `sent` و `failed` هستند.
- **بازیابی کرش:** worker قبل از ارسال، ردیف را lease می‌کند
  (`pending → sending`). بعد از ری‌استارت، leaseهای یتیم به `pending`
  برمی‌گردند و پیام دوباره ارسال می‌شود.
- **Retry:** خطاهای شبکه، 429 و 5xx با backoff نمایی و jitter تلاش مجدد
  می‌شوند؛ 429 دقیقاً `retry_after` پلتفرم را رعایت می‌کند. بعد از سقف
  تلاش، وضعیت `failed` و دلیل ثبت می‌شود.
- **Rate limit:** سه سطح سراسری/هر chat/هر کاربر با پنجرهٔ لغزان. پیام
  rate-limited با `defer` در صف می‌ماند و `attempts` مصرف نمی‌شود.
- **Offset:** offset هر پلتفرم در `poll_offsets` ذخیره می‌شود تا آپدیت
  تکراری یا گم نشود.
- **خاموشی تمیز:** SIGINT/SIGTERM باعث توقف polling، flush آلبوم‌ها، پایان
  ارسال در جریان و بستن اتصال‌ها می‌شود.
- **`/status`:** صف، خطاهای ۲۴ ساعت، آخرین رله، کاربران فعال و جفت‌های
  فعال را نشان می‌دهد.
- **پاک‌سازی محتوا:** بعد از تحویل موفق، `outbox.payload` بلافاصله به `{}`
  تغییر می‌کند؛ یعنی متن، کپشن و `file_id` دیگر در دیتابیس نمی‌مانند. ردیف
  بدون‌محتوا برای آمار نگه داشته می‌شود و بعد از
  `OUTBOX_SENT_RETENTION_DAYS` روز کاملاً حذف می‌شود. رکوردهای
  `messages` فقط شناسه‌اند (بدون محتوا) و برای reply/dedup باقی می‌مانند.
- **Health:** فایل heartbeat اتمیک برای `HEALTHCHECK` داکر.
- **تایم‌اوت رسانه:** timeout آپلود Telegram/Bale مبهم است؛ ممکن است فایل
  روی پلتفرم پذیرفته شده باشد. به‌طور پیش‌فرض `OUTBOX_MEDIA_TIMEOUT_TERMINAL=true`
  است تا به‌جای retry و ارسال تکراری، ورودی با دلیل `failed` شود. تایم‌اوت
  آپلود Telegram هم از ۲۰ ثانیهٔ پیش‌فرض PTB به ۶۰۰ ثانیه افزایش یافته است.
- **دکمه‌های شیشه‌ای:** callback queryها در هر دو adapter پارس می‌شوند،
  پاسخ داده می‌شوند (`answerCallbackQuery`) و منوی فعلی با
  `editMessageText` به‌روزرسانی می‌شود.

### کران تحویل

صف «حداقل یک‌بار» (at-least-once) است و پیام را گم نمی‌کند. اگر پروسه دقیقاً
بعد از پذیرش پیام توسط پلتفرم و قبل از ثبت `sent` بمیرد، چون Telegram/Bale
کلید idempotency ندارند، ممکن است همان یک پیام دوباره ارسال شود. خاموشی
تمیز این پنجره را در حالت عملیاتی عادی حذف می‌کند. برای رسانه، تایم‌اوت
آپلود به‌صورت پیش‌فرض terminal است تا حلقهٔ ارسال تکراری رخ ندهد؛ اگر
می‌خواهید در ازای احتمال تکرار، retry شود،
`OUTBOX_MEDIA_TIMEOUT_TERMINAL=false` بگذارید. برای جزئیات بیشتر
`tests/test_reliability.py`، `tests/test_media_relay.py` و بخش design در
کد را ببینید.

## ۱۶. چک‌لیست تست دستی

چک‌لیست کامل و قابل چاپ در
[`MANUAL_TEST_CHECKLIST.md`](MANUAL_TEST_CHECKLIST.md) قرار دارد. خلاصه:

1. تنظیم `.env` و بالا آمدن health.
2. `/start` و `/whoami` در هر دو پیام‌رسان.
3. `/pair` از یک طرف، `/pending` و `/accept` از طرف دیگر.
4. ارسال متن در هر دو جهت.
5. ارسال عکس در هر دو جهت.
6. ارسال فایل/document در هر دو جهت.
7. reply threading.
8. `/status` کاربر و مالک.
9. `/ban` و `/unban`.
10. `/unpair` و قطع رله.
11. ری‌استارت و بررسی باقی ماندن صف/offset.
12. تست rate limit با مقدار کوچک موقت.
13. بررسی نبود توکن/محتوا در لاگ INFO.
14. تست دکمه‌های شیشه‌ای: منوی اصلی، پذیرش/رد درخواست، پایان جفت و
    پنل مدیریت.
15. تست فایل/عکس بزرگ و بررسی اینکه یک نسخه (نه چند نسخه) برسد و در
    صورت timeout، ورودی `failed` شود نه اینکه حلقهٔ ارسال تکرار شود.

## محدودیت‌های شناخته‌شده

- ویرایش/حذف پیام‌ها بین دو پیام‌رسان منتقل نمی‌شود.
- webhook پشتیبانی نمی‌شود؛ فقط long polling.
- یک worker روی یک دیتابیس SQLite پشتیبانی می‌شود؛ horizontal scaling
  نیاز به تغییر مدل lease دارد.
- پیام‌های بالاتر از سقف پلتفرم تقسیم نمی‌شوند و به‌صورت notice گزارش
  می‌شوند.
- ارسال «دقیقاً یک‌بار» در بدترین حالت کرش بعد از پذیرش پلتفرم تضمین
  نمی‌شود (بخش کران تحویل).
